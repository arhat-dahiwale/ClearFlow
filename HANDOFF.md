# ClearFlow — Project Phase Handoff and Visualization Notes

## 1. Purpose and Project Workflow

ClearFlow is a data visualization and machine-learning project for multiclass DDoS detection using CICIDS-2017 and the SDN TCP-SYN dataset.

**Division of work:**
- **Python:** Data analysis, preprocessing, train/test splitting, feature selection, model training, evaluation, and SHAP computation.
- **Tableau/Power BI:** Visualizations built from the CSV exports generated by Python.
- **Shared responsibility:** Ensure that charts correctly represent the computed results and that the methodology is documented accurately.

This document records each phase's outputs, important decisions, visualization requirements, caveats, and handoff information. New phase sections will be appended in chronological order as the project progresses.

## 2. Cross-Phase Guidelines

1. **Use the correct source table.** Row counts, cell counts, class frequencies, and sampled feature values are different quantities. Do not treat them as interchangeable.
2. **Preserve dataset distinctions.** CICIDS-2017 DDoS and SDN TCP-SYN SYN Flood are different classes in this project.
3. **Distinguish representative data from visualization samples.** A sample designed to expose minority classes must not be used to report actual class frequencies.
4. **Choose visualizations based on analytical purpose.** Do not create charts merely to increase their number. Every chart must communicate a meaningful finding.
5. **Use Python-generated outputs.** BI tools should consume the provided CSV exports rather than independently reimplement the cleaning or modeling pipeline.
6. **Document methodological changes.** If a decision deviates from the agreed experimental design, record the rationale and implications.
7. **Prevent data leakage.** The test set must not determine cleaning parameters, class balancing, scaling parameters, or feature selection.
8. **Do not infer causation from correlation.** Correlated features may be redundant, but correlation alone does not establish that a feature should be removed.
9. **Respect the project's scope.** Each phase should produce its expected outputs before work proceeds to the next phase.

# Phase 02 — Preprocessing

## 1. Objective

**BI export directory:**

## 3. Preprocessing Operations

The pipeline performed the following operations:

1. Harmonized the feature names across both datasets.
2. Standardized raw labels into the intended modeling classes.
3. Removed rows with missing labels.
4. Excluded Heartbleed and Infiltration from the modeling dataset.
5. Removed rows containing missing or infinite numeric feature values.
6. Removed exact duplicate original records across files within each source dataset.
7. Identified and removed feature vectors with conflicting class labels.
8. Removed zero-variance features.
9. Exported the cleaned dataset, preprocessing summaries, feature audits, and BI visualization samples.

### Label decisions

- SDN `Normal` → `Benign`
- SDN `DDOS` → `SYN Flood`
- CICIDS-2017 `DDoS` remains a separate class.
- The three CICIDS-2017 Web Attack labels are merged into `Web Attack`.
- Heartbleed and Infiltration are excluded from modeling but retained in the raw-data visualizations.

### Feature decisions

- **Destination Port is retained.** Excluding it substantially increased ambiguous feature vectors, particularly for Benign and PortScan traffic. This is a documented deviation from the original plan to remove ports.
- `Fwd Header Length.1` is excluded because it was identical to `Fwd Header Length` in all eight CICIDS-2017 files.
- Flow IDs, IP addresses, source ports, protocol, and timestamps are excluded from predictive model inputs.
- `dataset` and `source_file` are retained as provenance metadata, but must not be supplied to models as predictive features.
- Seven zero-variance features were removed.

# Phase 03 — Fixed Train/Test Split

## 1. Objective

Create one reproducible training/test partition of the Phase 02 cleaned dataset. All subsequent experiment configurations must use these same partitions to ensure fair comparison.

## 2. Inputs and Outputs

**Input:**

`data/processed/cleaned_flows.csv.gz`

**Output datasets:**

- `data/processed/train.csv.gz`
- `data/processed/test.csv.gz`

**Export directory:**

`exports/phase03_split/`

## 3. Operations Performed

1. Read the cleaned dataset in chunks.
2. Hash the 70 model-feature values to identify identical feature vectors.
3. Verify that no feature group has conflicting target labels.
4. Generate five candidate folds using `StratifiedGroupKFold`, with shuffling and random seed `42`.
5. Select the fold with the best class balance, prioritizing the maximum per-class deviation from a 20% test share, followed by mean deviation and overall test-size deviation.
6. Write the selected training and test partitions while retaining `dataset` and `source_file` as provenance metadata.
7. Verify that no feature group is shared across the two partitions.

No class balancing, scaling, feature selection, or model training is performed in this phase.

| Total clean rows | 2,525,590 |
| Training rows | 2,020,546 |
| Test rows | 505,044 |

| Test percentage | 19.997% |
| Candidate folds evaluated | 5 |
| Selected fold | 5 |
| Model features | 70 |
| Unique feature groups | 2,522,744 |
| Feature groups shared across train/test | 0 |

## 6. Handoff Requirements for Subsequent Phases

- All experiments must reuse `train.csv.gz` and `test.csv.gz`. Do not generate a new split for different models, feature-selection methods, or random seeds.
- Exclude `dataset` and `source_file` from model inputs.
- Use only the 70 model features and the `Label` target.
- Apply class balancing only to training data.
- Fit scaling transformations on training data only, and apply them to test data without refitting.
- Fit feature-selection methods on training data only.
- Keep the test set untouched until model evaluation.
- Preserve the 12-class target definition established in Phase 02.

## 7. Caveats and Decisions

- The split is approximately 80/20, not exactly 80/20 for every class. Identical feature groups must remain together, which constrains the available group-aware stratified partitions.
- SYN Flood, Bot, and SSH-Patator have test proportions below 20%. Report the observed distribution rather than claiming an exact stratified 80/20 split for every class.
- The cleaned dataset remains naturally imbalanced. Class balancing has not been performed.
- The feature-group overlap check is zero, so no identical 70-feature input groups cross the train/test boundary according to the implemented hash-based check.
- The selected fold is fixed using seed `42` and must remain unchanged for all 200 experiments.

**Phase 03 is complete.** The fixed training/test datasets and split-verification exports are available for the next phase. No visualization deliverable is required for this phase.

# Phase 04 — Feature Selection

## 1. Objective

Rank the 70 candidate model features using three methods and define the fixed feature sets used in Phase 05.

## 2. Inputs and Outputs

- Input: `data/processed/train.csv.gz` only. The test split was not used for feature selection.
- Export directory: `exports/phase04_feature_selection/`
- Exact ordered feature lists: `exports/phase04_feature_selection/feature_sets.json`

## 3. Operations Performed

Three ranking methods were run on the same deterministic, class-capped sample drawn from the training split:

1. Random Forest impurity-based feature importance.
2. ANOVA F-test (`f_classif`).
3. Recursive Feature Elimination (RFE) using a Decision Tree.

The sample cap was 10,000 rows per class. Classes with fewer rows were retained in full. The resulting selection sample contained 70,245 rows.

This sample was used for feature ranking only; it did not replace or modify the fixed train/test split.
